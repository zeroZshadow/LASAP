# Test harness

How to build, run and observe the LAS mod without manual play. Scripts live in `scripts/`.

## Requirements

- Windows session **unlocked**. On a locked desktop the emulator stops presenting frames and the game loop stalls. Turning the monitors off is fine.
- Docker Desktop with the image `devkitpro/devkita64`; `build_exl.sh` pins it by digest (`IMAGE`), and the release workflow builds with the same.
- Python venvs created with `uv` (Python 3.12):
  - `.venv-ap`: Archipelago requirements (`vendor/Archipelago/requirements.txt`) plus pytest, and the patcher's `requirements.txt` for the world from source, with evfl and PyLibMS for the world's tests that read the mod's flowcharts.
  - `.venv-lasr`: the patcher's requirements with the asset build's (`patcher/requirements-assets.txt`: evfl, PyLibMS, oead, quicktex, Pillow on top of `requirements.txt`).
  - `.venv-relay`: PyInstaller, for `LASGhostRelay.exe` (README, Building a release).
- `vendor/Archipelago`: an Archipelago checkout, with a junction `vendor/Archipelago/worlds/las` → `apworld/las`.
  - Universal Tracker: `tracker.apworld` (FarisTheAncient/Archipelago releases) in `custom_worlds`, with an empty `Players` folder in `vendor/Archipelago` (without it, UT's settings open a folder browser). Headless, `launch("--nogui", "--list", "--name", <slot>, "--connect", <host:port>)` from `worlds.tracker.TrackerClient` logs the in-logic locations at error level; `sys.argv` must contain `--nogui` before the import.
- `scripts/local_paths.json` (gitignored): this machine's paths, with the keys of `scripts/local_paths.example.json`: `romfs` (the RomFS dump), `game` (the game file), `ryujinx` (the emulator), `ryujinx_logs`, `sandbox`, `re` (`main.bin` and the Ghidra project), `poptracker`, `lasr_brooty` (the PopTracker pack). `LASAP_ROMFS` comes before `romfs` and `LASAP_RE` before `re`. A tool stops with a message naming a key it needs and lacks; world tests that read the RomFS skip without `romfs`. A `--romfs` option defaults to `romfs`. `worktree.sh setup` copies the main checkout's file into a worktree.
- The RomFS dump for `test_map_positions.py`: `LASAP_ROMFS`, or `romfs` in `scripts/local_paths.json`; without either it is skipped.
- PopTracker for `poptracker_test.py`: a copy of the user's in the `app` folder of this machine's PopTracker folder (`poptracker` in `scripts/local_paths.json`), without its `packs`, in portable mode (`portable.txt`: config, saves and `log.txt` stay in its `portable-config` folder, never `%APPDATA%\PopTracker`), with `log` on and the update check and EmoTracker question answered in `portable-config\PopTracker\PopTracker.json`. It truncates `log.txt` on each start.

## Emulator: Ryubing (Ryujinx fork)

- **Binary:** `ryujinx` in `scripts/local_paths.json` (Ryubing Canary).
- **Game:** `game`, the 1.0.0 `.nsp`. The RomFS dump is `romfs`.
- **Sandbox data folder:** `ryujinx` in the sandbox folder (`sandbox`), a copy of the user's Ryujinx data (keys, firmware, saves). Tests never use `%APPDATA%\Ryujinx`. It contains `prod.keys`; never copy it into this repo. `emu.py` keeps it silent with SDL's dummy audio driver, as `--audio-volume 0` does not mute.
- **Translation cache:** `emu.py` starts the emulator with `--disable-ptc`, so no run uses code translated in an earlier one; `LASAP_PTC=1` keeps the cache on, as players have it (DESIGN.md, "Code the module writes"). Ryubing keeps it per build of the code files in the data folder's `games/01006bb00c6f0000/cache/cpu/0` (`1.0.0-<hash>.cache` and `.info`), with a backup in `cpu/1` that it loads when `cpu/0` has none; a run from an empty cache needs the build's files removed from both.
- **Logs:** the emulator writes logs to its own `Logs` folder (`ryujinx_logs`) even with `--root-data-dir`.
- **Closing:** headless Ryubing (`--no-gui`) ignores a window close; `emu.py stop` ends it by PID.
- **Playing in the sandbox:** with `LASAP_INPUT=config`, `emu.py start` takes player 1's input from the data folder's `Config.json` (its controller) instead of the keyboard alone. `ghost_relay.py --echo <dx>` sends each player its own frames back as a player `Echo`, `dx` units along x: a ghost that copies the person playing, through the client and the relay.
- **Sharing the sandbox.** There is one sandbox (data folder, `emu.pid`, port 43385, the e2e folder), so sessions working side by side take turns. Before deploying, resetting saves or starting the emulator, take it with `emu.py lock <owner>`; run those steps with `LASAP_SANDBOX_OWNER=<owner>`, and `emu.py unlock <owner>` when the test run is over. `emu.py start`/`stop`, `deploy_mod.sh` and `reset_saves.sh` refuse while another owner holds the lock. The test suite ("Test suite") runs on copies of the sandbox and leaves the sandbox itself alone; it takes the same lock.

## Working in a worktree

Sessions that change code work in their own git worktree and branch, so they never share a working tree or index. `vendor/`, the venvs, `patcher/exl/` and `patcher/exl-test/` are gitignored and exist only in the main checkout; `scripts/worktree.sh` (run in the worktree) covers the rest:

- `worktree.sh setup` adds an Archipelago worktree at `vendor/Archipelago` (from the main checkout's, at its commit) with `worlds/las` pointing at this worktree's world, and copies the main checkout's built modules into `patcher/exl/` and `patcher/exl-test/` with their build times, so `build_release.py` and `suite.py` show a module older than the source; run `build_exl.sh` in the worktree when they do. The venvs are used from the main checkout by path (`<main>/.venv-ap/Scripts/python.exe`, `<main>/.venv-lasr/...`); nothing links to them, so deleting a worktree cannot reach them. `ap.py`, `las_client.py`, `build_exl.sh` and `reload_exl.sh` work from the worktree.
- `worktree.sh test [pytest args]` runs the world's tests on this worktree's world.
- `worktree.sh land <subject> [<line> [<line>]]` puts this branch on `master` as one commit with that message (a subject, at most two lines under it), made in the worktree so `master` only fast-forwards, then removes the Archipelago worktree; the branch then points at that commit. When `master` has moved on it rebases the branch onto it and stops: rerun the tests, land again (on conflicts: resolve, `git rebase --continue`, test, land). It refuses when the worktree has uncommitted changes, or when the main checkout has uncommitted edits in files the branch changes (another session is working there: land after it has committed). Its other uncommitted edits are left alone.
- `worktree.sh teardown` removes the Archipelago worktree without landing.

The sandbox is shared with every other session: take the lock (Emulator, "Sharing the sandbox"). A local MultiServer outside a sandbox run uses a port of its own, not the default 38281.

## Test suite

`scripts/suite.py` (in `.venv-ap`) runs the sandbox tests of `scripts/tests/suite.txt` on several emulator instances side by side (`-j`, default 4), and the world's tests (pytest) beside them (`--no-world` skips them); names of groups run only those. It needs the lock free or held by `LASAP_SANDBOX_OWNER`, the suite's mod installed in the sandbox (`deploy_mod.sh`) and this checkout's test module built (`build_exl.sh`); it refuses a test module older than the module's source. The suite's mod is the `make_test_patch.py` patch of `suite.txt`'s `mod:` options: `suite.py` makes that patch (`suite/suite.aplas` in the sandbox folder) and refuses to run when the installed `config.ini`'s `seed_hash` is not its seed hash, printing the commands that patch and install it. The mod comes from this checkout's patcher: one patched by an older patcher lacks the files later patcher changes write (`itemget_pose` needs the seed file's `models`).

- **Groups.** A line of `suite.txt` is a group: `<group> [<section>.<key>=<value> ...] [<seed sections>.txt ...] [client|ghost]: <script> ...`. Its scripts run in order in one emulator, each leaving the game as the next expects, starting from the new-game snapshot's saves with the sandbox's mod, this checkout's test module, the group's `config.ini` options (read at boot, so a group per setting) and its seed file sections: each of its files in `scripts/tests/seed` (`shuffles.txt`) replaces the seed file's sections it holds. The mod is the same for every seed's options (DESIGN.md, Options), so the option groups change only `config.ini`. `client` starts the LAS client fed from the instance's `cmds.txt`; `ghost` also starts a ghost relay and `ghost_peer.py --secret test` fed from `peer_cmds.txt`, and joins the client to the relay. Every group gets a fresh emulator and session.
- **Instances.** Instance n (1 and up) lives in the sandbox folder's `suite\<n>`: `ryujinx` (a copy of the sandbox's data folder without its translation caches, made on the first run; delete it to copy again), `emu.pid` and `e2e`. Its game port is 43385 + 10·n (the debug port 100 above, the relay 6 above). Each run copies in the sandbox's `Config.json`, mod and the checkout's `subsdk9`.
- **Output.** A line per group as it ends: PASS or FAIL, the instance and each script's seconds (the first script's time includes the emulator's start); for a failure, the end of its log. Logs go to `suite\logs\<group>.<script>.log` and `world.log`. `suite\times.json` keeps each group's last time; the longest run first.
- **Timing** (2026-10-23, 715 s of group time): 188 s with 4 instances, 168 s with 5, the world's tests (115 s) beside them. A boot to a level takes about 28 s (`boot_file1`) and 36 s (`newgame_file2`) with four emulators running, 12 s of it before the game's first frame; one emulator alone boots in 23 and 30 s.
- **Game speed.** Ryubing's `--vsync-mode Unbounded` runs the game several times faster (about 260 frames a second on the title), but scripts that poll STATE from Python then miss short states (`itemget_timing` failed at its `msg:Opening`) and the timing checks lose their meaning, so the emulators run at the Switch's rate.

## Observing and driving the game

- **Guest log.** Module output (`[AP] ...`, `[exlaunch|...]`) goes to the emulator log via `svcOutputDebugString`.
- **Screenshots.** `emu.py shot` uses `PrintWindow`; it works while the window is covered or unfocused.
- **Debug commands** exist only in the test build ("Building the exlaunch module"): `DBG ...` on the debug port (the game port + 100, 43485 in the sandbox) or the game socket, `/dbg ...` in the LAS client (`/dbg`, `/game`, `/patch`, `/play`, `/start`, `/setting` and `/setup` exist in a client run from source, not in the release world). The debug port answers within milliseconds; the client's `/dbg` path is slower, as the client polls its stdin.

  A debug command's reply goes to the debug client that sent it. Lines for the AP client that a command causes (`CHECK`, `CHECKS`, `HINT`, `GOAL`, `DIED`, `DEATHDROPPED`, `RECV`, `LOG`) also go to the AP client, so the server sees the check a `give` or `collect` makes.

  Button bits follow `nn::hid::NpadButton`: A `1`, B `2`, X `4`, L+R `c0`, Plus `400`, Minus `800`, D-pad left/up/right/down `1000`/`2000`/`4000`/`8000`. The stick range is ±32767. Buttons from `input` and `press` are added to the physical ones in the game's input poll.
- **Inputs.** Press when the game's state takes the press ("Game state") rather than after a delay: a press the game drops leaves no trace, a press it takes changes a state within a few frames.
- **Buttons in tests.** B is the sword (holding it charges a spin). Dismiss text with B next to signs and NPCs: A also starts a new "Check" or "Talk". Git Bash rewrites arguments that start with `/`; set `MSYS_NO_PATHCONV=1` for `e2e.py cli /las`.
- **Sandbox port.** The sandbox game listens on 43385, so it runs beside the user's own modded game on 43384. Start the scripted client with `--game-port 43385`. A sandbox install done by the client (Patch tab) writes no port, so that game uses 43384.
- **Scripted AP session.** Run the client and server with stdin fed from a file (`tail -n0 -f cmds.txt | ...`) so `/dbg`, `/las`, `/game` and server `/send` commands can be appended while they run. `e2e.py` writes to these files in the folder `LASAP_E2E` names (default the sandbox folder's `e2e`). `/game <line>` sends a raw protocol line, e.g. a hand-made `ITEM` or `NAME`. For texts naming another player, generate a two-slot seed (a second slot with a small game such as ChecksFinder) and send its items with `/send` or `/release`. Start MultiServer with `--release_mode goal --collect_mode goal` to keep a goal from releasing every location. A run that starts over needs a clean slate in this order: the game stopped and the saves reset (the client reads the collected checks from the SD card), every client of the session stopped (a client still running sends the checks it knows to a new server), the server's `.apsave` deleted, then the server and client started.
- **Script ops.** `e2e.py run <script> [trace file]` scripts (`scripts/tests/*.txt`) drive the game on the debug port and check it between steps; a failed step stops the script with the STATE line, and so does an `ALERT` (a guard tripped: Link died, or a script's own `guard`). Each line prints with the seconds since the script started, and the run ends with `SCRIPT OK in <s> s`. Conditions are the module's ("Game state").
  - `${NAME}` in a line is the environment variable `NAME`; the script stops when it is not set.
  - `connect [s]`: wait for the debug port (the game has started). `expect HELLO [s]`: wait until the AP client is connected, also when it connected before the script started. `expect <regex> [s]`: a debug reply or client log line since the last send; it reads the debug port only briefly before it turns to the client log. `poll <regex> <s> <DBG line>`: send the DBG line until a reply matches, for state the module changes a frame or more later.
  - `send <line>`: a `DBG` line goes to the debug port, anything else to the client's stdin. `logged <regex> [s] [client|server|peer] [count]`: wait for log lines since the script started. `logcount <regex> <n> [client|server|peer]`: stop unless exactly n lines logged since the script started match (0: none). `peer <command>`: a command for the DeathLink peer. `game <line>`: a protocol line to the game on the debug port, as the client sends it (a hand-made `ITEM`). `stall`: connects to the game port as a client that sends `PING` and reads nothing, until the script ends (no LAS client may be connected). `srv <server command>`: a MultiServer console command, e.g. `/send_location "<player>" <location>` (a player name with spaces in quotes). Arguments are split on spaces, so patterns use `\s`. `wait <s>`: sleep, only for checking that something stays as it is.
  - `until <condition> [s]`: wait until a condition holds. `tap <buttons> [down] [up] [lx ly] [when <condition> [ms]]`, `tapuntil <buttons> <until> [when <condition>] [s]`, `hold <buttons> <lx> <ly> until <condition> [s]`, `interact [buttons] [s]`, `choose <option> [s]`: the module ops of the same name. `guard <condition>` / `guard off <condition>`: the module's guards.
  - `face up|down|left|right`: hold the stick until Link faces that way (he may take a step).
  - `select <slot>`: in the file menu, move the cursor to a slot (0 = file 1).
  - `dismiss [s]`: close the open text with B, holding B while pages print; fails at a choice and when there is no text. `advance [buttons] [s] [fast]`: the same, stopping at a choice.
  - `free [s]`: wait until the player can move, no item-get shows or waits and no message holds him. `loaded [s]`: the same in a level entered after the last `send` or input op. `inlevel [s]`: a level entered after the last `send` or input op has loaded. `level <name>`: stop unless the player is in that level.
  - `state`, `shot <png>`: print the STATE line, capture the window (a relative path is in the sandbox folder). `check <regex>`: stop unless the STATE line matches. `await <s> <regex>`: wait until it matches.
  - `warp <level> <x> <y> <z>`: reload a level there (through another level when it is the current one) and wait (it waits for a free player first: send `DBG warp` for a swimming Link, event state 30). `goto <x> <y> <z>`: teleport within the loaded room and wait until Link stands there. `at <x> <z> [tol]`: stop unless the player stands there.
  - `gotodrop [s]`: wait until the drop actor whose `Fall` ran last (DBG `drop`) is active and stands still, then put Link against it on his side, which picks it up (no wait for him to settle, as the pickup's event starts at once). `droprest [s]`: wait until it is at rest or gone (picked up, out of the world) once it was there, or taken as it lands on Link, printing each new position; fails when neither happens in time.
  - `screen`, `press <buttons> <ms> <screen> [tries]`, `mash`: timed presses through `input`, for scripts that have no state to wait for.

- **Warps and pits.** Warp into a dungeon or house from `Field`: after a warp out of `TownWell` (Link standing in water) the screen can stay black until the emulator restarts. `pos` also sets the respawn point, so a `pos` over a pit makes Link fall again on every respawn until he dies; reset with a warp to another level and back.
- **Health.** `poke 84 1c00` sets health to 7 hearts (quarter hearts, u16).
- **Tarin's gift.** The detain scene on leaving the house only stops Link; talk to Tarin (A at about (9.4, 0, 6.0) in his house) to get the gift.
- **Finding a location.** LASR's `Randomizers/*.py` map locations to rooms (`CHEST_ROOMS`, `HEART_ROOMS`, ...); `leb_actors.py` prints the actors there. Teleport one tile (1.5) south of a chest and press A facing up. A `pos` into a room that is not loaded lands on no floor; `warp` loads the target's room. A bush (`ObjGrass`), rock or pot is solid: Link teleported onto one stands on top of it, a tile above the floor, and cannot reach what is below. Pick the target tile from `leb_actors.py <room> --near <x> <z>`, which lists the actors around the object with their offsets in tiles, on a tile with none of them (tall grass, `ObjLawn`, is walkable); when every tile next to the object holds one, teleport to the nearest free tile and cut or lift the one in between first. `warp` and `goto` stop the script when Link lands more than 1 above the target or away from it. A test that needs no enemies sends `DBG enemies kill` once it has arrived, so none knock Link out of what he does.

## Game state

The test build reports the game's state so tests press when the game takes a press instead of after a delay.

- **STATE** has `ghosts` (ghost slots in use), `music` (the jukebox's track, `-` none), `zonebgm` (the zone's track as the BGM manager holds it), `bgm` (the tracks playing, `name:kind`, `-` none), `bgmvol` (their volume targets in percent) and `layers` (the instruments the Jukebox's Ballad's tracks are set for, in hex, bit i the instrument of dungeon i + 1; `-` while it does not play), `muted` (1 while the Jukebox mutes the music) and `puppets=<drawn>/<with an actor>` (ghost slots whose puppet is drawn, its model loaded / that have an actor) and `gear=<shapes>/<tunic>/<eye>,<mouth>,<ear>/<upper>` (ghost slot 0's puppet: the shapes it draws, in hex as the wire has them, the tunic, face frames and upper-body animation set, -1 none yet; `-` while not drawn) and `tags` (per ghost slot, its name tag: `-` none, `h` hidden, `g` shown while the font draws the name's glyphs, `d` drawn) before the frame fields. It ends with `frame` (frames since boot: a pass of the game's main loop each, menus included, counted at its first input poll; before the loop runs every 16 ms, and while a pass lasts every 100 ms), `msg` (the message window's state), `choice` (its cursor, 0 = first option), `face` (`up`, `down`, `left`, `right`, from Link's rotation) and `yaw` (degrees, 0 = down), `anim` (the animation Link plays, as its `PlayerAnimation.gsheet` file name), `file` (the file menu's cursor), `entry` (the name entry's cursor: 0 on the name, 1 on OK) and `read` (frames the last page spent in `Reading`).
- **Fields** conditions test: `screen`, `level`, `event` (Link's state number, PLAYER.md's state table: 0 when he stands, 9 a dash, 22 demoEvent; not whether an event runs), `paused`, `free`, `lock` (the game's controller ignores input), `pad` (the controller's buttons), `show` (an item-get waits or shows), `text` (the message window's state with its wait counter, `KeyWaiting,6/6`), `choice`, `client`, `server`, `file`, `face`, `carry`, `health`, `entry`, `anim` (STATE's `anim`), `zone` (Link's zone, actor `+0xb0`: the camera room he is in, -1 none; ACTORS.md).
- **Conditions** (`await`, `press ... when`, script ops): `<field>=<value>`, `<machine>:<state>` (`title:WaitLR`, `files:DataSelectKeyWait`, `msg:KeyWaiting`), `free` (Link can move, no item-get pending, no message holds him; one in `EventWaiting` does not), `unlocked`, `textready` (the open message waits for a button and takes one now), `choiceready` (a choice takes buttons now), `dead` (in a level with no health), `navi=<state>` (the pause menu header's state: 1 Open, 2 WaitKey, 3 Selected, 4 CloseOldUi, 5 Close; `-` with the menu closed). `!` negates; `+` joins (`choice=1+choiceready`).
- **UI state machines.** The title (`title`), the file menu (`files`), the message window (`msg`), its choices (`choice`), the file and name screens (`file`, `name`), the overworld and dungeon maps (`map`, `dmap`), the fishing rod and lure (`lure`: `Wait`, `Casting`, ..., `HitWait`, `HitRetrieveHold`, `Catch`, `Lost`) and each fishing pond fish (`fish`: `Wait`, ..., `Catching`, `MoveAngry`, `Get`, `MoveEscape`) are learned from their state changes and named by their own state tables; `DBG ui` lists them.
- **Trace.** `DBG trace on` (or `e2e.py run <script> <trace file>`) sends `T <ms> <frame> <what>` on every change of a field, a UI machine's state, the buttons each frame's input polls carried (`hid phys=<buttons> inj=<buttons>`), every press and op step, and watched memory.
- **What takes a press** (2026-10-14, Ryubing, game 1.0.0, sandbox):
  - The intro takes a tap about 20 frames after the title's machine appears; earlier taps change nothing.
  - The title takes L+R on the first frame of `WaitLR` with the controller unlocked, a 2-frame tap is enough.
  - The file menu takes A on the first frames of `DataSelectKeyWait` and of `DataSelectConfirm`; Up/Down move the cursor one slot per tap.
  - The message window takes a button in `KeyWaiting` once its wait counter reaches its limit, 6 frames after it enters the state (10 in `PreSelecting`). A choice (`Selecting`) takes buttons once its layout animation ends; an A on the sixth frame of `Selecting` was dropped.
  - Holding B while a page prints shows it whole; with Instant Text a page needs 1–3 frames of `Reading`.
- **Boot timeline** (2026-10-14, `newgame_file2` with Instant Text, from the debug port's first trace line): intro to title machine 0.85 s, title fade-in to `WaitLR` 1.1 s, title to file menu 1 s, file menu to `DataSelectKeyWait` 0.8 s, two A's 0.4 s, the file loads in 2.4 s, Tarin's house loads in 0.6 s; Marin's wake-up scene runs 6.2 s before her first line, the lines and the scene's end take 4 s. Link is free 18.2 s after the intro shows.

## Reverse engineering

- `DBG dumpmain` writes the decrypted, relocated main module from memory (runtime base 0x8504000 on Ryubing). Keep it in the `re` folder (`re` in `scripts/local_paths.json`), outside the repo.
- `re/scan.py` finds strings, the code that loads a string's address, and callers of a function, using module offsets (the ones `InstallAtOffset` takes). Event actions are dispatched by name, so `xstr <action name>` leads to the action's handler. `strs <off>` lists the strings a function loads; `sms` lists the UI state machines (their `ChangeState` functions, state names and callers).
- UI state machines (game 1.0.0): u32 frames in the state `+0x8`, u8 state `+0xd` (0xff none), previous state `+0xe`, owner `+0x40`; per state an enter, update and exit member function from `+0x48`, `0x30` apart; the state names follow the table (`re/UI.md`, State machines).
- Ghidra (scoop `ghidra`): `re/decomp.sh` imports `main.bin` raw (AARCH64 little endian, base 0x8504000, no auto-analysis) into a project next to it (`LASAP_RE`, default `re`), names it from `re/las.sym` (`re/ghidra/ImportSymbols.java`) and decompiles the functions at the given offsets (`re/ghidra/Decomp.java`); the project opens read-only, so each run starts from the plain import. An offset given as `<offset>:<hex word>` puts that instruction there first: in the dump each function the running module hooks starts with the hook's branch (`Inventory_AddItemID` begins `sub sp, sp, #0x50`, `0x8d08e0:d10143ff`).
- `re/las.sym` names the functions, globals and vtables found so far, in the `.sym` format of Ghidra's former `ImportSymbolsScript.py`: `<name> <absolute address> f|l [note]`, f a function, l a label. In the Ghidra GUI, `re/ghidra/ImportSymbols.java` (Script Manager, script directory `scripts/re/ghidra`) imports it into a program imported at base 0x8504000. Each finding adds its symbols there; the docs below describe structures and fields.
- `re/UI.md` describes the game's UI framework (layout wrappers, state machines, UI ids, input, UI datasheets) and the map pages (cursor, markers, pins, overworld and dungeon maps); `re/bflyt_tree.py <layout>` prints a layout's pane tree from the RomFS dump.
- `re/ACTORS.md` describes the game's actors: the actor table (`scan.py actors` lists it), the entity and actor classes and their vtable slots, creation (`Actor_Create`, the factories), the flags, the entity manager's task queues and the frame's phases, destruction, rooms (loading, streaming, zones, dungeon reloads, level jumps) and what persists (LEB switches, the removal memory, appear checks).
- `re/ITEMS.md` describes what adding and owning each item id does (`Inventory_AddItemID`, `Inventory_HasItem`), the chamber stones (their tables, the panel each one gives, their vanilla sources and Dampé's part) and the saved data (the save image, its header, the current data).
- `re/MODELS.md` describes the g3d model objects, the model instances, the skeletal and instanced model components and the animation components; `re/PLAYER.md` Link's actor, his states, his character controller and his animation controller; `re/FRAMEWORK.md` the framework (its lifecycle, scheduler and phases), the camera and the audio manager.
- `re/EVENTS.md` describes the event manager (its queue, requests and signals), the event and its flow over evfl's flowchart context, how a flowchart's actors, actions and queries bind to the system actors and to actors' EventCharas (`event/common.evhb`'s hierarchy), and what an event's start does to the actors.
- The module's `game/` headers type these objects field by field; the docs above give the evidence for the fields and what the headers' comments leave out.
- `DBG event` prints the event manager's queue and its signals' connections, and for the running event its entry, flowchart, flow (its back pointers), actor map (each name with `c` a chara or `s` a system actor, `a`/`q` its lookups) and the first flowchart's bindings (`<actor>:<c or -><bound actions>/<actions>`).
- `DBG flow <flowchart> <entry>` requests that entry of `event/<flowchart>.bfevfl` with Link and the system actors (`AP::Bridge::RequestEvent`); the flowchart's other actors are not in the event.

## Building the exlaunch module

The module is `las-ap-exl` (from Owen-Splat/exlaunch, GPL-2.0). Run `bash scripts/build_exl.sh`; it builds two modules:

- The release module (`patcher/exl/`), which the patcher installs for players. It has no debug commands, debug port, trace or input injection.
- The test build (`patcher/exl-test/`, `make BUILD=build-test DEFINES=-DLASAP_TEST`), which `deploy_mod.sh` and `reload_exl.sh` install in the sandbox. Everything tests need beyond the game lives under `#ifdef LASAP_TEST`: the test build's own code in the module's `test/` folder, and small probes in the features' files.

## Why Ryubing, not Eden

Eden (yuzu fork) offers no decisive advantage (assessed 2026-10-12):
- Randovania's Dread exlaunch socket mod officially supports only Ryujinx.
- Eden's airplane mode (`airplane_mode`) breaks TCP sockets while it is on.
- Eden's TAS player runs only in the Qt frontend.
